=====================================================================
 INSTRUÇÕES PARA SUBIR O PROJETO TOGGLEMASTER NA AWS (CONTA ZERADA)
=====================================================================

Contexto do projeto:
- 5 microsserviços: auth-service, flag-service, targeting-service,
  evaluation-service, analytics-service
- Cada um roda em K8s (namespace próprio) e é exposto via
  Ingress -> ingress-nginx -> Service (ClusterIP) -> Pods
- auth-service, flag-service, targeting-service usam Postgres
  (rodando como Pod dentro do cluster, com PVC)
- evaluation-service usa Redis (Pod dentro do cluster) + SQS
- analytics-service usa DynamoDB (AWS de verdade) + SQS
- Todas as imagens de produção apontam para o ECR:
  798350130470.dkr.ecr.us-east-1.amazonaws.com/<servico>:latest
- Region usada nos manifests: us-east-1

A conta está zerada (nem VPC existe). Por isso a ordem abaixo importa:
rede -> identidade/acesso -> cluster -> registro de imagens ->
banco/fila/tabela -> apps -> ingress -> dns.

Pré-requisitos na sua máquina antes de começar:
- AWS CLI v2 instalado e configurado (aws configure) com um usuário
  IAM (não o root da conta) que tenha permissão de administrador
  só para esse setup inicial
- kubectl instalado
- eksctl instalado (facilita demais criar VPC + EKS juntos)
- helm instalado (para ingress-nginx e outros addons)
- Docker instalado (para build e push das imagens)

=====================================================================
ETAPA 0 - IAM (identidade e acesso)
=====================================================================
Motivo: a conta só existe, então nem usuário de trabalho existe ainda.
Nunca use o usuário root da conta no dia a dia.

1. No console AWS (ou via CLI), crie um usuário IAM (ex: "devops-admin")
   com política AdministratorAccess só para esta fase de setup.
2. Gere Access Key + Secret Key para esse usuário e rode:
     aws configure
   Preencha Access Key, Secret Key, region "us-east-1" e output "json".
3. Depois que o cluster estiver de pé (etapa 2), você vai trocar o uso
   de Access Key/Secret Key hardcoded nos Pods por IRSA (IAM Role for
   Service Account) - isso é tratado na ETAPA 6, não pule.

=====================================================================
ETAPA 1 - VPC (rede)
=====================================================================
Motivo: EKS precisa rodar dentro de uma VPC com subnets públicas
(para o LoadBalancer do ingress) e privadas (para os nós/pods, boa
prática de segurança).

Opção mais simples: deixar o eksctl criar a VPC junto com o cluster
(ele já cria VPC, subnets públicas/privadas, route tables, NAT
Gateway e Internet Gateway sozinho). Por isso a ETAPA 1 e a ETAPA 2
acontecem no mesmo comando abaixo - não crie a VPC manualmente a
menos que você já tenha um desenho de rede específico em mente.

Se quiser criar a VPC manualmente antes (mais controle, mais trabalho):
- 1 VPC (ex: 10.0.0.0/16)
- 2 subnets públicas em AZs diferentes (ex: 10.0.0.0/20, 10.0.16.0/20)
- 2 subnets privadas em AZs diferentes (ex: 10.0.128.0/20, 10.0.144.0/20)
- 1 Internet Gateway anexado à VPC
- 1 NAT Gateway (numa subnet pública) para as subnets privadas saírem
  para a internet (pull de imagem, chamadas à AWS, etc)
- Route tables: pública aponta 0.0.0.0/0 -> Internet Gateway,
  privada aponta 0.0.0.0/0 -> NAT Gateway
- Marcar subnets com as tags que o EKS exige:
    kubernetes.io/cluster/<nome-do-cluster> = shared
    kubernetes.io/role/elb = 1                (subnets públicas)
    kubernetes.io/role/internal-elb = 1       (subnets privadas)

Recomendação: use o eksctl (ETAPA 2) e deixe ele cuidar disso.

=====================================================================
ETAPA 2 - EKS (cluster Kubernetes)
=====================================================================
Motivo: é onde todos os 5 serviços vão rodar. Sem cluster, nada dos
manifests em k8s/prod/nuvem/ funciona.

1. Crie um arquivo cluster.yaml:

   apiVersion: eksctl.io/v1alpha5
   kind: ClusterConfig
   metadata:
     name: togglemaster-cluster
     region: us-east-1
     version: "1.30"
   vpc:
     nat:
       gateway: Single
   managedNodeGroups:
     - name: ng-default
       instanceType: t3.medium
       desiredCapacity: 3
       minSize: 2
       maxSize: 6
       volumeSize: 20
       privateNetworking: true
   iam:
     withOIDC: true   # ESSENCIAL: habilita IRSA (etapa 6)

2. Rode:
     eksctl create cluster -f cluster.yaml
   Isso demora de 15 a 20 minutos. Ele cria VPC, subnets, IGW, NAT,
   o control plane do EKS e os node groups (as EC2 que rodam os pods).

3. Confirme o acesso:
     kubectl get nodes
   (o eksctl já escreve o kubeconfig automaticamente)

4. Instale o EBS CSI Driver (necessário para os PVC dos Postgres,
   que usam storageClassName: gp3 nos manifests de prod/nuvem):
     eksctl create addon --name aws-ebs-csi-driver \
       --cluster togglemaster-cluster --region us-east-1 \
       --force

   Depois confirme que existe uma StorageClass chamada "gp3"
   (alguns clusters vêm só com "gp2" por padrão):
     kubectl get storageclass
   Se não existir "gp3", crie:
     kubectl apply -f - <<EOF
     apiVersion: storage.k8s.io/v1
     kind: StorageClass
     metadata:
       name: gp3
     provisioner: ebs.csi.aws.com
     volumeBindingMode: WaitForFirstConsumer
     parameters:
       type: gp3
     EOF

=====================================================================
ETAPA 3 - ECR (registro de imagens Docker)
=====================================================================
Motivo: os Deployments de prod/nuvem já apontam para
798350130470.dkr.ecr.us-east-1.amazonaws.com/<servico>:latest -
mas numa conta zerada esse repositório ECR não existe ainda, e é
o número da conta (798350130470) que você precisa confirmar/trocar
pelo ID da SUA conta AWS (aws sts get-caller-identity).

Repita para cada um dos 5 serviços (auth-service, flag-service,
targeting-service, evaluation-service, analytics-service):

1. Criar o repositório:
     aws ecr create-repository --repository-name auth-service --region us-east-1
     aws ecr create-repository --repository-name flag-service --region us-east-1
     aws ecr create-repository --repository-name targeting-service --region us-east-1
     aws ecr create-repository --repository-name evaluation-service --region us-east-1
     aws ecr create-repository --repository-name analytics-service --region us-east-1

2. Login do Docker no ECR:
     aws ecr get-login-password --region us-east-1 | \
       docker login --username AWS --password-stdin \
       <SEU_ACCOUNT_ID>.dkr.ecr.us-east-1.amazonaws.com

3. Build + tag + push de cada serviço (exemplo com auth-service,
   repita trocando o nome/pasta para os outros 4):
     docker build -t auth-service ./auth-service
     docker tag auth-service:latest \
       <SEU_ACCOUNT_ID>.dkr.ecr.us-east-1.amazonaws.com/auth-service:latest
     docker push \
       <SEU_ACCOUNT_ID>.dkr.ecr.us-east-1.amazonaws.com/auth-service:latest

4. IMPORTANTE: se o SEU_ACCOUNT_ID for diferente de 798350130470,
   atualize a linha "image:" em todos os arquivos:
     auth-service/k8s/prod/nuvem/auth-service-deployment.yaml
     flag-service/k8s/prod/nuvem/flag-service-deployment.yaml
     targeting-service/k8s/prod/nuvem/targeting-service-deployment.yaml
     evaluation-service/k8s/prod/nuvem/evaluation-service-deployment.yaml
     analytics-service/k8s/prod/nuvem/analytics-service-deployment.yaml

=====================================================================
ETAPA 4 - SQS (fila usada por evaluation-service e analytics-service)
=====================================================================
Motivo: os ConfigMaps já referenciam uma fila fixa:
  https://sqs.us-east-1.amazonaws.com/798350130470/fiap-analytics-service
Essa fila não existe numa conta zerada - precisa ser criada com esse
nome (ou você atualiza os ConfigMaps com o nome/conta corretos).

1. Criar a fila:
     aws sqs create-queue --queue-name fiap-analytics-service --region us-east-1

2. Pegar a URL real gerada (troque 798350130470 pelo seu account id):
     aws sqs get-queue-url --queue-name fiap-analytics-service --region us-east-1

3. Atualizar AWS_SQS_URL nestes dois arquivos com o valor real:
     analytics-service/k8s/prod/nuvem/analytics-service-configmap.yaml
     evaluation-service/k8s/prod/nuvem/evaluation-service-configmap.yaml

=====================================================================
ETAPA 5 - DynamoDB (usado por analytics-service)
=====================================================================
Motivo: em produção (prod/nuvem) o analytics-service não usa mais o
dynamodb-local do docker-compose, ele fala com o DynamoDB real da AWS.
O ConfigMap já espera uma tabela chamada "ToggleMasterAnalytics".

1. Criar a tabela (mesmo schema usado no docker-compose):
     aws dynamodb create-table \
       --table-name ToggleMasterAnalytics \
       --attribute-definitions AttributeName=event_id,AttributeType=S \
       --key-schema AttributeName=event_id,KeyType=HASH \
       --billing-mode PAY_PER_REQUEST \
       --region us-east-1

2. Confirme:
     aws dynamodb describe-table --table-name ToggleMasterAnalytics --region us-east-1

=====================================================================
ETAPA 6 - IAM para os pods acessarem SQS/DynamoDB (IRSA)
=====================================================================
Motivo: hoje os secrets de analytics-service e evaluation-service têm
AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY fixos no YAML (em texto
puro). Isso funciona, mas NÃO é a prática correta em produção -
o comentário "# Pode passar via IRSA" já está nos próprios
deployments como lembrete. Prefira IRSA: o pod recebe permissão
temporária da AWS sem nenhuma chave gravada em lugar nenhum.

1. Criar uma IAM Policy com acesso só ao necessário (SQS + DynamoDB
   da tabela/fila específicas, não AmazonSQSFullAccess genérico).

2. Criar um Service Account no K8s associado a essa policy via eksctl
   (repita para analytics-service e evaluation-service, trocando
   namespace/nome):
     eksctl create iamserviceaccount \
       --cluster togglemaster-cluster \
       --namespace analytics-service \
       --name sa-analytics-service \
       --attach-policy-arn <ARN_DA_POLICY_CRIADA> \
       --approve

3. No Deployment do analytics-service e evaluation-service, adicionar:
     spec:
       template:
         spec:
           serviceAccountName: sa-analytics-service
   e remover as env vars AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY
   (o SDK da AWS dentro do container passa a pegar credenciais
   automaticamente via IRSA).

4. Depois disso, os Secrets opaque-analytics-service e
   opaque-evaluation-service podem perder essas duas chaves -
   deixe só o que sobrar de fato sensível (ex: SERVICE_API_KEY).

OBS DE SEGURANÇA: as chaves AWS que estão hoje em texto puro nos
arquivos analytics-service/k8s/prod/nuvem/analytics-service-secrets.yaml
e evaluation-service/k8s/prod/nuvem/evaluation-service-secrets.yaml
devem ser rotacionadas (desativadas/recriadas no IAM) assim que
possível, independente de ter ido para o Git ou não - elas já
existem em texto puro no disco.

=====================================================================
ETAPA 7 - Ingress Controller (nginx) no cluster de nuvem
=====================================================================
Motivo: os manifests de Ingress usam ingressClassName: nginx, mas o
controller em si não está nos manifests do projeto - precisa ser
instalado à parte, igual foi feito no seu cluster local.

1. Instalar via Helm (ele cria automaticamente um Service do tipo
   LoadBalancer, que na AWS provisiona um Elastic Load Balancer):
     helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
     helm repo update
     helm install ingress-nginx ingress-nginx/ingress-nginx \
       --namespace ingress-nginx --create-namespace

2. Confirme que o LoadBalancer foi criado e pegue o endereço público:
     kubectl get svc -n ingress-nginx ingress-nginx-controller
   (o campo EXTERNAL-IP vai mostrar um hostname *.elb.amazonaws.com)

=====================================================================
ETAPA 8 - Deploy dos serviços (aplicar os manifests)
=====================================================================
Motivo: agora sim os manifests de k8s/prod/nuvem/ de cada serviço
podem ser aplicados. A ordem importa: namespace -> banco/fila/config
-> deployment -> service -> ingress. Comece por auth-service porque
flag-service e targeting-service dependem dele (AUTH_SERVICE_URL).

Para CADA serviço, na ordem: auth-service, flag-service,
targeting-service, evaluation-service, analytics-service:

  kubectl apply -f <servico>/k8s/prod/nuvem/<servico>-namespace.yaml
  kubectl apply -f <servico>/k8s/prod/nuvem/<servico>-configmap.yaml
  kubectl apply -f <servico>/k8s/prod/nuvem/<servico>-secrets.yaml
  # só auth-service, flag-service, targeting-service têm PV/PVC/postgres:
  kubectl apply -f <servico>/k8s/prod/nuvem/<servico>-pvc.yaml
  kubectl apply -f <servico>/k8s/prod/nuvem/postgres-db-<servico>-pod.yaml
  # evaluation-service usa redis em vez de postgres:
  kubectl apply -f evaluation-service/k8s/prod/nuvem/redis-evaluation-service-pod.yaml
  kubectl apply -f <servico>/k8s/prod/nuvem/<servico>-deployment.yaml
  kubectl apply -f <servico>/k8s/prod/nuvem/<servico>-svc.yaml
  kubectl apply -f <servico>/k8s/prod/nuvem/<servico>-hpa.yaml
  kubectl apply -f <servico>/k8s/prod/nuvem/<servico>-ingress.yaml

Depois de cada serviço, confira antes de ir pro próximo:
  kubectl get pods -n <servico>
  kubectl get ingress -n <servico>
Espere os pods ficarem "Running" e "1/1 Ready" (o readinessProbe
bate em /health) antes de seguir para o próximo serviço.

=====================================================================
ETAPA 9 - Testar o acesso via nginx
=====================================================================
Pegue o hostname do LoadBalancer (ETAPA 7) e teste cada rota:

  curl http://<hostname-do-elb>/auth/health
  curl http://<hostname-do-elb>/flags/health
  curl http://<hostname-do-elb>/targeting/health
  curl http://<hostname-do-elb>/evaluation/health
  curl http://<hostname-do-elb>/analytics/health

Se todos responderem, os 5 serviços estão de pé, atrás do nginx,
como no ambiente local.

=====================================================================
ETAPA 10 - DNS (opcional, mas recomendado)
=====================================================================
Motivo: o hostname do ELB é feio e pode mudar. Para produção de
verdade:

1. Registrar/ter um domínio (ex: togglemaster.com) numa Hosted Zone
   do Route 53.
2. Criar um registro tipo A (Alias) apontando para o ELB do
   ingress-nginx (Route 53 tem suporte nativo a alias para ELB).
3. Se quiser HTTPS, instalar o cert-manager no cluster e emitir
   certificado via Let's Encrypt, ou usar um ACM Certificate anexado
   diretamente ao Load Balancer (mais comum quando o ELB é um NLB/ALB
   gerenciado pelo AWS Load Balancer Controller em vez do
   Service LoadBalancer padrão do ingress-nginx).
